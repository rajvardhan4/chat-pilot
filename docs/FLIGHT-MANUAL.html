01

What this is

A multi-tenant AI chatbot platform, sold to businesses, delivered onto their WordPress sites.

Two programs, and understanding the split explains almost every design decision in the codebase.

SystemRuns onOwns
Chat Pilot Cloud
Node.js		 Hostinger shared hosting, behind Passenger Accounts, AI provider keys, knowledge base, the answering engine, conversations, leads, analytics, plans, and the admin console
Chat Pilot for WordPress
PHP plugin		 each customer's own WordPress site Drawing the chat widget and relaying messages over a signed connection. One secret: the Site API Key.

The plugin is deliberately thin. It holds no AI key, no knowledge, no system prompt. If a customer's WordPress site is compromised, the attacker gets one revocable key scoped to one website — not the AI account, not other customers.

That is also why the setup order is not optional: the Cloud has to be running and configured before the plugin has anything to connect to.

BCustomer + websitein the portal
CAI connectedtheir provider key
DKnowledge addedFAQs, pages, docs
ESite key issuedcp_live_…
FPlugin connectedwidget goes live
i
Each customer brings their own AI key

AI usage is billed to the customer's own OpenAI/Anthropic/Gemini account, not to the platform. One customer on Claude and another on Groq is normal — the provider is chosen per website.

Two functions carry the entire tenant boundary

requireAccountAccess() in accounts.ts and getWebsiteForAccount() in websites.ts. Both return 404, not 403, for another tenant's id — a 403 would confirm the record exists. Any new route that touches customer data must go through one of them. This is the most important invariant in the codebase.

Database access

Everything goes through src/db/mongo.ts. No service imports the MongoDB driver directly.

saas/src/db/mongo.tsthe whole surface
// every collection read/write goes through this
col('websites').findOne({ _id: id })

// multi-document atomicity (needs a replica set — Atlas always is one)
await withTransaction(async (session) => { ... })

// called once at startup: connects, pings, ensures 44 indexes
await connectDb()

32 collections, named exactly as the old SQL tables were. Every document's _id is the application's own opaque id string, never a Mongo ObjectId. There are no schema migrations — indexes are re-ensured at every startup, which is idempotent.

!
The client is pinned to Stable API v1 with strict: true

That keeps an Atlas upgrade from silently changing a driver default under production traffic — but it also rejects commands outside API v1. .distinct() is one of them; use an aggregation with $group instead. This has already bitten once, on the admin audit page.

i
Why so little is editable in WordPress

Provider, model, knowledge, instructions, widget design, forms, conversations and analytics all live in the Cloud. Two editable copies of that data is how a site ends up saying one thing while the engine believes another. The plugin displays and relays; it does not edit.

How the plugin finds the Cloud

In precedence order:

  1. CHAT_PILOT_API_URL defined in wp-config.php — pins it at server level; the admin screen then shows it read-only, so nobody with only wp-admin access can redirect this site's signed traffic.
  2. The built-in default in chat-pilot.php, currently the live Hostinger address.
!
The built-in default is a temporary domain

chat-pilot.php ships pointing at palevioletred-louse-364639.hostingersite.com. When the Cloud moves to a permanent domain, change that line, rebuild the plugin, and re-upload it to every site that has not pinned the constant. Doing it now, at three sites, is much cheaper than doing it at thirty.

06

Onboarding a customer

Eight steps, once per customer. Step 4 decides whether the chatbot is any good.

  1. Account

    The customer signs up at /signup, or you do it for them. The signup form only ever creates a customer account, never an admin.

  2. Website

    My Websites → Add website, with the site's real URL.

    !
    The domain you enter is the only domain the key will work on

    If the live site is www.example.com, register that, not the bare domain. Getting it wrong means the plugin connects and then refuses every message with domain_mismatch.

  3. AI provider

    AI Providers → pick the vendor, paste the customer's key, Test connection & find models, then choose a model from the ones the test actually discovered. A provider cannot go live until its test has passed, so a mistyped key can never leave the site pointing at an AI that does not answer.

  4. Knowledge

    Start with a website scan for coverage, then add FAQs for everything that must come out word-perfect. Four sources, and when two disagree the higher one wins:

    PrioritySourceUse it for
    1 — highestFAQExact question, exact answer. Prices, hours, policies.
    2Manual knowledgeFacts you type in that live nowhere on the site.
    3Uploaded documentsPDF, DOCX, TXT, MD, CSV — brochures, price lists, spec sheets.
    4 — lowestWebsite scanBulk background from the customer's pages. Good coverage, weakest authority.
    !
    Skip this and the bot answers nothing

    With no knowledge, retrieval finds nothing and every real question returns the fallback sentence. That is exactly the state all three live websites are in right now — see live state today.

  5. Instructions

    AI Instructions — tone, answer length, and the fallback wording. The bot never invents an answer; it falls back. Write that sentence in the customer's voice.

  6. Preview

    Developer Chat Preview runs the identical engine with diagnostics showing what retrieval matched. If it answers well here, it will answer well on the site. If it falls back here, fix the knowledge now, not later.

  7. Site API Key

    Connection → Generate key. A label like "WordPress" helps when you are later looking at a list of keys. Copy it immediately. You can issue several per website and revoke any one without touching the others.

  8. Plugin

    Upload the ZIP on the customer's site, activate, paste the key, Connect.

09

What happens on one visitor message

The path a question takes, and where it can stop early.

1
Visitor types in the widgetWidget JS posts to WordPress admin-ajax, not to the Cloud. The browser never learns the Cloud's address or any key.
2
Plugin signs the requestHMAC-SHA256 over METHOD\nPATH\nTIMESTAMP\nNONCE\nsha256(body), using the Site API Key.
3
Cloud verifiesKey hash, timestamp window, nonce replay cache, body hash, and that the calling domain matches the registered one.
4
Account and website checksAccount active, subscription active, website active. Each failure is a specific error code, not a generic one.
5
IntentA greeting or small talk is answered without touching the provider at all — no tokens spent.
6
RetrievalSearch this website's knowledge only. Nothing found → return the fallback, still without calling the provider.
7
GenerateDecrypt the customer's provider key, assemble the prompt from instructions plus retrieved documents, call the vendor.
8
RecordStrip HTML from the answer, store conversation and message, count tokens, estimate cost, check the budget.
9
ReplyThe visitor receives { text, status } and nothing else — no diagnostics, no model name, no key.
✓
Steps 5 and 6 are why a token bill can be zero

Greetings and unanswerable questions never reach the provider. On the live system today, all seven AI requests cost nothing at all, because there is no knowledge for retrieval to find.

10

Verify it actually works

Four checks. Do all four before telling a customer it is live.

  1. Plugin says Connected

    Chat Pilot → Dashboard. Provider configured, knowledge documents above zero, widget enabled, website active.

  2. The widget appears

    Open the customer's site in a private window. The launcher should be in the corner.

  3. It answers a real question

    Ask something you know is in the knowledge base. A fallback here but a good answer in Developer Chat Preview means the plugin is talking to a different website's configuration — check the key.

  4. It shows up in the Cloud

    Conversations should list that chat and Analytics should count the request. If the widget answered but nothing was recorded, it is serving a stale cache — press Sync widget settings.

Running it locally

Node 22.18+ and a MongoDB. Nothing else to install.

  1. Install
    saas/once
    $ npm install
$ cp .env.example .env
  2. Get a MongoDB

    Either point MONGODB_URI at Atlas, or start a throwaway one — it prints the connection string to paste into .env:

    saas/leave running
    $ npm run mongo:local

    It is a single-member replica set, not a standalone mongod, because the app uses transactions — and because every Atlas cluster is one, so local matches production.

  3. Secrets, then seed and start
    saas/once, then daily
    $ node -e "for (const k of ['ENCRYPTION_KEY','SESSION_SECRET','SITE_KEY_PEPPER']) console.log(k+'='+require('crypto').randomBytes(32).toString('hex'))"
$ npm run seed
$ npm start
[chat-pilot] SaaS portal listening on port 4000

    Use npm run dev instead to reload on save.

  4. Make yourself an admin
    saas/once
    $ npm run admin:create -- --email you@example.com --name "Your Name"

    Prints a generated password once. Pass --password to choose your own.

!
Port 4000 already in use

An older server is still running. On Windows pkill will not kill it — use PowerShell:

Get-NetTCPConnection -LocalPort 4000 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }

The three builds

Three destinations, three shapes. They are siblings, not alternatives.

CommandProducesFor
npm run hostinger:build dist/hostinger/…zip
compiled JavaScript, flat		 What is live now. Shared hosting behind Passenger. Files at the ZIP root because the panel points "Application root" at the folder holding package.json.
npm run cloud:build dist/cloud/…zip
TypeScript source, nested		 A VPS you have root on. Unpacks to chat-pilot/saas/ + deploy/, matching docs/DEPLOY.md.
npm run plugin:patch
plugin:minor / plugin:major		 dist/plugin/chat-pilot-X.Y.Z.zip The customer's WordPress site. The bump variants edit the version first, in both places it lives, and refuse to build if the two disagree.

Why the Hostinger build compiles and the others do not

Everywhere else, Node runs the TypeScript directly by stripping types — no build step to forget. That needs Node 22.18+. Hostinger's shared plans run Passenger on older Node, which cannot load a .ts file at all: the process dies and the panel shows a 503 with nothing in it mentioning TypeScript. So build-hostinger.mjs runs tsc first. tsconfig.json already sets rewriteRelativeImportExtensions, so import './app.ts' becomes './app.js' in the output and the emitted tree needs no patching. The floor is then Node 20.19, set by the MongoDB driver rather than by us. That build also strips devDependencies from the shipped package.json, so a plain npm install on the server cannot pull mongodb-memory-server and download a MongoDB binary onto shared hosting.

!
Always bump the plugin version when you change the plugin

WordPress caches plugin CSS and JS by version number. Ship a change without a bump and the admin screen looks broken in a way nothing in the code explains. plugin:patch for fixes, plugin:minor for behaviour changes, plugin:major for breaking ones. To set an exact version: node scripts/build-plugin.mjs --set 2.3.4.

Updating the plugin on a live site

Plugins → Add New → Upload Plugin → choose the new ZIP → Install Now. WordPress sees chat-pilot is already installed and offers Replace current with uploaded — take it. The Site API Key and every setting survive.

!
Do not Delete the plugin to update it

Deleting runs uninstall.php, which removes the Site API Key, the connection state and the cached widget config by design. The site then has to be connected again with a fresh key. Delete is for removing Chat Pilot, not for upgrading it. An earlier version of this guide had this wrong, and it silently disconnected sites on every documented update.

Environment

Every process.env read in the Cloud happens in src/config/env.ts and nowhere else.

VariableNotes
MONGODB_URIRequired in production. Atlas connection string.
MONGODB_DBDatabase name. chatpilot in production.
ENCRYPTION_KEYRequired. Decrypts every stored AI provider key.
SESSION_SECRETRequired. Signs portal session cookies.
SITE_KEY_PEPPERRequired. Verifies every Site API Key.
APP_URLPublic address. Used in emails and dashboard links.
PORTLocal only. Must not be set on Hostinger.
FORCE_HTTPS + TRUST_PROXYBoth true behind a proxy. Only the first → infinite redirect loop.
MAIL_TRANSPORTlog today: notifications are recorded but never sent.
SUPERADMIN_EMAIL / _PASSWORDRead by npm run seed only, to create the first admin.
RATE_LIMIT_*, UPLOAD_*, PROVIDER_TIMEOUT_MSSensible defaults; change only if real traffic demands it.
!
The three secrets are not recoverable, and they are your backup

ENCRYPTION_KEY is the only thing that opens the customer AI keys sitting encrypted in Atlas. Lose it and the database stays perfectly healthy while every provider key in it becomes permanently unreadable, and every installed plugin disconnects. The app refuses to start in production without all three — deliberately, because a missing secret should fail loudly rather than fall back to a throwaway value and silently destroy data.

The production values live in dist/hostinger/chat-pilot-hostinger.env on the maintainer's machine and in the Hostinger panel. That is not a backup. Put them in a password manager, today.

Tests

183 tests across 12 files. They boot the real app and drive it over HTTP; only the AI provider is mocked.

saas/before every commit
$ npm test
ℹ tests 183   ℹ pass 183   ℹ fail 0

$ npm run typecheck

npm test goes through scripts/run-tests.mjs, which starts one in-memory MongoDB replica set and points every test file at it. Each test file runs in its own process and gets its own database, named chatpilot_test_<pid>.

!
Run tests only through npm test

node --test directly fails loudly rather than quietly reaching for whatever mongodb://127.0.0.1:27017 happens to resolve to. A test run also ignores .env entirely — deliberately, because inheriting MONGODB_DB from it once collapsed all twelve files onto a single database and broke isolation silently.

10-wordpress-plugin.test.ts runs the real plugin PHP against the real server on a minimal WordPress shim. It skips, loudly, when PHP is not installed — which is the case on the current development machine, so that file's assertions are not currently being exercised.

Troubleshooting

Things that have already cost someone a day. Read before debugging.

You seeWhat it meansFix
503 from Hostinger, nothing in the logs The Node process is not running, or Passenger cannot reach it. Check PORT is not set in the panel. Then Node version, then stderr.log.
SSL alert number 80 / server selection timed out Atlas is refusing this IP. Not a code problem. Atlas → Network Access. Also check the cluster is not paused.
bad auth The connection string still has <db_username> in it, or the password has an unencoded @ : / ? #. Rebuild the URI from Atlas → Connect → Drivers.
"Chat Pilot could not be reached" Transport failure — the request never arrived anywhere. The address is wrong or unreachable, not the key. Check the Cloud address and that it resolves from the WordPress machine. A bad key gives a different error.
"That does not look like a Site API Key" What was submitted is not a cp_live_ key — usually the browser autofilled a saved password over the field. Clear the field and paste the key again. Fixed properly in v2.3.1.
Site API Key vanished after an update The plugin was Deleted rather than replaced; uninstall.php wipes it by design. Issue a fresh key. Next time use Replace current with uploaded.
Connects, then every message fails Domain mismatch. The key is bound to the registered domain. Compare Registered domain and This site on the Connection tab. www counts.
Infinite HTTPS redirect FORCE_HTTPS=true without TRUST_PROXY=true. Set both.
Widget answers the fallback every time Nothing in the knowledge base matched. Not a provider failure. Check knowledge_documents. Ask the same question in Developer Chat Preview.
Provider stuck on "Invalid Credential" The AI provider rejected the key — expired, revoked, or wrong provider. Re-create it in that provider's console and save again. The status detail says which.
"Quota Limited" or "Rate Limited" The key works; the customer's AI account is out of credit or throttled. The customer tops up or waits. Nothing to fix on your side.
Widget does not appear at all Disabled locally, hidden by a page rule, or hidden for logged-in admins. Plugin Chat Widget tab, then Cloud Chat Widget. Check in a private window.
Ownership shows "Not verified" The Cloud could not read /wp-json/chat-pilot/v1/site-token — HTTP auth, a firewall, or a staging password. Cosmetic. The connection works; only the badge is affected.
Admin page 500s after adding a Mongo query A command outside Stable API v1 — .distinct() is the usual one. Use an aggregation with $group.
Tests fail or hang only together Something broke per-file database isolation again. Check a test run still ignores .env.
Plugin screen looks broken after a change Cached CSS or JS from the previous version. You skipped the version bump. Rebuild with plugin:patch.

For anything else: the plugin's Settings → Plugin log records the WordPress side with keys redacted. In the Cloud, Master Admin → System Health and Audit Log cover the server side.
